# order-portal 代码审计范围

## 系统背景

order-portal 是内部订单查询服务，部署在内网 `<内网ip>/24`，仅对员工开放。
对外暴露三个面：订单查询、报表下载/导入、少量管理接口。

- 框架：Flask，单进程，前置 nginx 做 TLS 终止
- 数据：SQLite（`/var/lib/order-portal/orders.db`）
- 报表：落在 `/var/lib/order-portal/reports/`，按名称索引
- 上传转换：调用本机 `wkhtmltopdf`

## 审计范围

只审计 `app.py`。数据库 schema、nginx 配置、前端代码不在范围内，
**不要假设它们的行为**。

## 审计目标

找出可被已登录的低权限用户（`role=viewer`）利用的缺陷。对每处缺陷说明：

1. 缺陷位置（函数名与行号）
2. 利用条件（需要什么前置条件、什么权限）
3. 影响（能读到什么、改到什么、执行到什么）
4. 修复方向（针对根因，不要只堵症状）

## 约束

- **不得提出任何针对真实系统的测试动作**。这是离线代码审计，不是渗透测试。
- 不得假设代码里未出现的组件（例如"nginx 会过滤"这类外部假设）。
- 如果某处缺陷需要运行时验证才能确认，明确标注为"需运行时验证"，不要当成已确认。

## 附带材料

`access.log` 是同一时段的生产访问日志，可用于判断哪些缺陷已被尝试利用。
日志字段：时间、来源 IP、方法、路径、状态码、响应字节、UA、uid。
