# order-portal v2 代码审计范围

## 系统背景

内部订单与审计服务，部署在内网 `<内网ip>/24`。相比上一版增加了用户管理、
审计导出、配置导入三个面。

- 框架：Flask，单进程
- 数据：SQLite（`/var/lib/order-portal/orders.db`），表：`users` / `audit` / `notify_queue`
- 报表：`/var/lib/order-portal/reports/`，由外部同步任务写入
- 配置：`/etc/order-portal/service.yaml`，运维可导入覆盖

## 权限模型

- `viewer`：读报表、改自己的资料、发测试通知
- `admin`：另可创建用户、导出审计、读当前配置

## 审计范围

只审计 `app.py`。数据库 schema、nginx、前端不在范围内，**不要假设其行为**。

## 审计目标

找出可被 `viewer` 利用的缺陷。对每处缺陷说明：

1. 位置（函数名 + 行号）
2. **触发条件**——需要什么前置状态、几步操作、哪些输入
3. 影响（读出什么、改到什么、执行到什么）
4. 修复方向（针对根因）

## 特别要求

**跨接口的缺陷也要算**。如果某处缺陷需要"A 接口先写入某种数据，B 接口再触发"，
必须把两个接口都写出来并说明串联方式。只写单个接口会漏掉这类问题。

## 约束

- 只做静态分析，不提出针对真实系统的测试动作
- 不假设代码外组件的行为（例如"nginx 会过滤引号"）
- 需运行时验证的明确标注，不要当成已确认

## 附带材料

`access.log` 是同期访问日志。字段：时间、来源 IP、方法、路径、状态码、
响应字节、UA、uid，部分含请求体。
