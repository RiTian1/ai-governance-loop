## 2. 测试金字塔中的集成测试定位

### 2.1 分层比例

```
        ▲
       /E2E\          10%  — 端到端测试（关键业务路径）
      /─────\
     /集成测试\        20%  — 集成测试（模块间真实交互）
    /─────────\
   /  单元测试  \      70%  — 单元测试（纯逻辑验证）
  /─────────────\
```

**约束**：
- 推荐比例：单元测试 70%、集成测试 20%、E2E 测试 10%
- E2E 测试占比超过 20% 必须提供书面理由并经技术负责人确认
- 每次架构评审应检查当前测试分层比例
- 新增功能模块必须同时提交对应层级的测试
- **禁止用 E2E 测试替代本应由单元测试覆盖的纯逻辑验证**

### 2.2 集成测试的职责边界

| 测试类型 | 职责 | 不应做 |
|---------|------|--------|
| **单元测试** | 纯逻辑验证、边界条件、异常处理 | 访问网络、数据库、文件系统 |
| **集成测试** | 模块间真实交互、外部依赖集成、契约验证 | 验证纯逻辑、覆盖所有边界条件 |
| **E2E 测试** | 关键业务路径、用户场景 | 验证边界条件、覆盖所有功能 |

## 3. 集成测试具体约束

### 3.1 核心原则

**来源**：`domains/automation/test-pyramid.md` 第 3 节

1. **验证真实交互**
   - 集成测试应验证模块间的真实交互
   - 优先使用测试容器（Testcontainers 等）模拟外部依赖
   - 禁止在集成测试中使用 Mock 替代真实依赖（应在单元测试中 Mock）

2. **契约测试**
   - 对于第三方 API，应使用契约测试（Contract Test）验证接口兼容性
   - 契约测试确保 API 消费方和提供方的接口约定一致
   - 参考：`agents/specialists/api-tester.md` 提供契约测试实施指导

3. **CI 自动化**
   - 集成测试必须在 CI 环境中可自动执行
   - **禁止依赖手动启动的外部服务**
   - 应使用容器化或 IaC 自动启动依赖服务

4. **前置与清理**
   - 每个集成测试必须包含明确的前置条件设置（Setup）
   - 必须包含后置清理（Teardown）
   - 测试结束后不应残留脏数据

5. **失败诊断**
   - 集成测试的失败消息必须包含足够的上下文信息以定位交互问题
   - 应记录：请求参数、响应内容、依赖服务状态、网络日志

### 3.2 测试容器（Testcontainers）使用

**推荐场景**：
- 数据库集成测试（PostgreSQL, MySQL, MongoDB）
- 消息队列集成测试（Kafka, RabbitMQ, Redis）
- 第三方服务模拟（Localstack for AWS, Azurite for Azure）

**约束**：
- 容器镜像版本应与生产环境一致或接近
- 容器启动超时应合理配置（建议 60 秒）
- 容器应在测试结束后自动清理
- CI 环境必须支持 Docker-in-Docker 或 Docker Socket 挂载

### 3.3 契约测试（Contract Testing）

**适用场景**：
- 微服务间 API 调用
- 前后端接口约定
- 第三方 API 集成

**工具推荐**：
- Pact（消费者驱动契约测试）
- Spring Cloud Contract
- OpenAPI Spec 验证

**约束**：
- 契约文件必须纳入版本控制
- 契约变更必须经过双方确认
- 契约测试应在 CI 中自动执行

## 4. 测试数据管理

### 4.1 工厂模式

**来源**：`domains/automation/test-data.md` 第 1 节

- 测试数据应通过 Factory 或 Builder 模式程序化生成
- **禁止在测试代码中硬编码大段数据**
- 数据工厂必须支持默认值覆盖
- 共享的数据工厂应集中管理在 `tests/factories/`

**示例**：
```python
# 推荐
user = UserFactory.create(email="test@example.com")

# 禁止
user = {
    "id": 1,
    "name": "Test User",
    "email": "test@example.com",
    "created_at": "2025-01-01T00:00:00Z",
    # ... 50 行硬编码数据
}
```

### 4.2 数据库隔离

**来源**：`domains/automation/test-data.md` 第 5 节

- 每个测试用例应在独立事务中运行，测试结束后自动回滚
- 若无法使用事务隔离，应为每个测试分配独立的数据库实例或 Schema
- **禁止多个测试共享可变的数据库状态**
- 数据库迁移脚本必须在测试环境中自动执行
- 测试结束后不应残留脏数据

### 4.3 敏感数据脱敏

**来源**：`domains/automation/test-data.md` 第 3 节

- 测试数据中禁止包含真实的 PII、API 密钥、密码或访问令牌
- 必须使用脱敏工具或占位符生成器
- CI 环境中的测试凭证必须通过密钥管理服务注入
- 从生产环境导出的测试数据必须经过完整脱敏处理

### 4.4 种子可控

**来源**：`domains/automation/test-data.md` 第 4 节

- 涉及随机数据的测试必须支持通过固定种子（Seed）重现
- 随机种子值必须在测试失败日志中输出
- 默认应使用固定种子运行测试
- 基于随机数据的测试失败后，必须先用相同种子重现

## 5. 测试证据要求

### 5.1 证据格式

**来源**：`domains/automation/test-evidence.md` 第 1 节

- 测试报告必须以结构化格式输出：JUnit XML、JSON 或 CI 兼容格式
- 报告中必须包含：测试名称、执行结果、执行耗时、失败原因
- 纯文本日志仅作为补充，不得作为唯一证据
- 自定义报告格式必须提供 Schema 定义文件

### 5.2 日志采集

**来源**：`domains/automation/test-evidence.md` 第 3 节

- 测试失败时必须自动采集被测系统的相关日志
- 日志采集范围应限定为测试执行期间
- 应保留最近 10 次运行的完整日志
- 日志中的敏感信息必须在采集时自动脱敏
- 日志文件应按运行批次组织：`<日期>/<运行ID>/<测试名>/`

### 5.3 可重现性要求

**来源**：`domains/automation/test-evidence.md` 第 4 节

- 每份测试证据必须附带完整的执行命令
- 证据中必须记录执行环境信息：OS、运行时版本、依赖版本
- 使用容器化环境的测试应记录镜像标签或 Dockerfile 哈希值
- 证据中应包含代码版本标识（Git 提交哈希）

### 5.4 归档规则

**来源**：`domains/automation/test-evidence.md` 第 5 节

- 测试证据的默认保留期限为 90 天
- 关键发布版本的证据应永久保留
- 每份归档证据必须关联到对应的变更标识
- 归档证据应支持按变更、时间范围或测试套件检索
- 归档操作应自动化执行

## 6. Flaky 测试治理

### 6.1 Flaky 定义

**来源**：`domains/automation/flaky-test-policy.md` 第 1 节

- Flaky 测试：代码未变更的情况下，多次运行结果不一致
- 仅因环境配置错误导致的持续失败不属于 Flaky
- 在特定平台上稳定失败应标记为平台兼容性问题
- Flaky 状态的判定应基于数据（如最近 N 次运行的通过率）

### 6.2 检测机制

**来源**：`domains/automation/flaky-test-policy.md` 第 2 节

- CI 流水线应对每个失败的测试自动执行至少 2 次重试
- 重试后通过的测试应标记为疑似 Flaky
- 应建立 Flaky 测试仪表盘，持续追踪每个测试的历史通过率
- 通过率低于 95% 的测试应自动标记为 Flaky 并创建追踪工单
- 检测窗口应至少覆盖最近 20 次运行

### 6.3 修复时限

**来源**：`domains/automation/flaky-test-policy.md` 第 3 节

- 标记为 Flaky 的测试必须在 2 个冲刺（Sprint）内完成修复或做出处置决定
- 高优先级（P0/P1）业务路径上的 Flaky 测试必须在 1 个冲刺内修复
- 修复 Flaky 测试应优先于开发新测试
- 每个冲刺的回顾会议应包含 Flaky 测试数量和趋势的汇报

### 6.4 临时跳过约束

**来源**：`domains/automation/flaky-test-policy.md` 第 4 节

- 跳过（Skip/Disable）Flaky 测试必须附带对应的 Issue 链接和指定负责人
- 跳过注释必须包含跳过日期和预计修复日期
  - 格式：`@skip(issue=#123, owner=张三, eta=2025-05-01)`
- 未附带 Issue 链接的跳过操作应在代码审查中被阻断
- 跳过超过 30 天仍未修复的测试，应触发自动告警

### 6.5 根因分类

**来源**：`domains/automation/flaky-test-policy.md` 第 6 节

常见根因分类：
- 竞态条件（Race Condition）
- 外部依赖不稳定
- 时间敏感逻辑
- 资源竞争
- 测试间状态泄漏

**处理策略**：
- 根因为外部依赖不稳定的，应推动引入 Mock 或契约测试替代
- 根因为竞态条件的，应检查是否存在共享状态或不当的并发假设

## 7. CI/CD 门禁

### 7.1 环境特定门禁

**来源**：`domains/devops-ci/pipeline-gates.md` 第 2 节

| 环境 | 必须通过 | 可选 |
|------|---------|------|
| **开发环境（Dev）** | 编译、单元测试 | 集成测试、代码覆盖率 |
| **测试环境（Staging）** | 所有阻断级门禁、集成测试、端到端测试 | 性能基线测试 |
| **生产环境（Prod）** | 所有测试（单元、集成、E2E、性能）、安全扫描、人工审批 | — |

### 7.2 阻断级门禁

**来源**：`domains/devops-ci/pipeline-gates.md` 第 1.1 节

以下检查失败必须阻断构建：
- 编译失败
- 单元测试失败
- 代码覆盖率低于项目基线（建议 ≥ 70%）
- 静态代码分析发现严重缺陷（Critical/High）
- 安全扫描发现高危漏洞（CVSS ≥ 7.0）
- 许可证合规检查失败
- **API 契约校验失败（实现与契约不一致）**

### 7.3 测试环境准入规则

**来源**：`domains/devops-ci/environment-policy.md` 第 2.2 节

**测试环境（Test/QA）准入条件**：
- 通过 Dev 环境验证
- **集成测试通过**
- 部署频率：每日或每次 PR 合并后
- 数据要求：使用测试数据集，接近生产数据结构
- 访问控制：开发团队 + QA 团队可访问

## 8. 阶段治理要求

### 8.1 测试集成阶段

**来源**：`02-phase-governance.md` 第 7 节

**目标**：
- 验证功能、平台适配、安装编译链路、启动行为和回归证据

**最低输出**：
- 测试范围与环境矩阵
- 前置动作执行记录
- smoke、回归、适配、安装验证结果
- 未覆盖项与降级说明

**约束**：
- **每次启动集成测试前必须检查环境准备动作是否完成**
- 静态测试描述、前置功能概括和验收变化若在该阶段才被明确，必须立即回注

### 8.2 详细设计阶段

**来源**：`02-phase-governance.md` 第 5 节

**约束**：
- 详细设计不得缺失测试前置动作和环境准备说明
- 必须包含：测试前置动作与静态测试描述

## 9. 验证政策对齐

### 9.1 证据优先级

**来源**：`04-verification-policy.md` 第 3 节

```
1. 结构化自动化输出          ← 最高优先级（集成测试报告）
2. 可复现的构建或测试日志
3. 人工验证的结构化记录
4. 临时截图或录屏
5. 口头描述                  ← 最低优先级
```

### 9.2 验证维度

**来源**：`04-verification-policy.md` 第 2 节

- 规则语义与运行时行为
- **跨集成兼容性**
- 自动化回归与人工验证证据
- 打包、制品、发布与回滚可执行性

### 9.3 降级场景

**来源**：`04-verification-policy.md` 第 4 节

以下情况视为降级验证：
- 无法在当前环境运行目标构建或关键回归
- **只验证了局部模块，未覆盖受影响集成面**
- 缺少结构化证据，只能给出人工结论
- 涉及制品或发布路径，但未验证回滚或兼容性

## 10. 快速参考卡片

### 10.1 集成测试检查清单

```markdown
## 集成测试实施检查清单

### 测试设计
- [ ] 测试覆盖模块间真实交互（非 Mock）
- [ ] 使用测试容器（Testcontainers）模拟外部依赖
- [ ] 第三方 API 使用契约测试验证
- [ ] 每个测试包含明确的 Setup 和 Teardown
- [ ] 失败消息包含足够的上下文信息

### 测试数据
- [ ] 使用 Factory 模式生成测试数据
- [ ] 每个测试在独立事务中运行或使用独立 Schema
- [ ] 测试数据已脱敏，不包含真实 PII
- [ ] 随机数据使用固定种子，可重现
- [ ] 测试结束后无残留脏数据

### 测试证据
- [ ] 测试报告为结构化格式（JUnit XML/JSON）
- [ ] 失败时自动采集日志
- [ ] 证据包含执行命令和环境信息
- [ ] 证据关联到代码版本（Git 提交哈希）
- [ ] 证据已归档，保留期限符合要求

### CI 集成
- [ ] 集成测试可在 CI 环境中自动执行
- [ ] 不依赖手动启动的外部服务
- [ ] 容器镜像版本与生产环境一致
- [ ] 测试超时配置合理（建议 60 秒）
- [ ] 失败测试自动重试 2 次以检测 Flaky

### Flaky 治理
- [ ] 通过率低于 95% 的测试已标记为 Flaky
- [ ] Flaky 测试已创建追踪工单
- [ ] 跳过的测试附带 Issue 链接和负责人
- [ ] Flaky 测试在 2 个冲刺内修复或处置
- [ ] 根因已分类并记录

### 门禁合规
- [ ] 测试环境部署前集成测试已通过
- [ ] 生产环境部署前所有测试（单元+集成+E2E）已通过
- [ ] API 契约校验已通过
- [ ] 测试覆盖率达到项目基线（≥ 70%）
```

## 总结

集成测试在治理框架中的定位：
1. **测试金字塔的中间层**：占比 20%，验证模块间真实交互
2. **使用测试容器**：模拟外部依赖，确保 CI 可自动执行
3. **契约测试**：验证 API 接口兼容性
4. **数据隔离**：独立事务或独立 Schema，测试结束后无残留
5. **证据驱动**：结构化报告、日志采集、可重现性
6. **Flaky 治理**：2 个冲刺内修复，跳过需附 Issue
7. **CI 门禁**：测试环境必须通过集成测试，生产环境必须通过所有测试

**核心原则**：集成测试应聚焦模块间交互，而非替代单元测试或 E2E 测试的职责。
