# 设计评审流程

## 1. 设计评审目的

- 确保设计方案满足业务需求和技术约束
- 发现设计中的风险、盲点和不一致
- 促进知识共享和团队对齐
- 记录设计决策和评审意见

## 2. 评审触发条件

### 2.1 必须评审
- 新系统或子系统设计
- 影响多个服务的接口变更
- 数据模型重大变更
- 安全相关的设计变更
- 性能关键路径变更

### 2.2 可选评审
- 单服务内部重构
- 技术债务清理方案
- 非核心功能设计

## 3. 评审前准备

### 3.1 作者准备
- 设计文档（可以是 RFC、ADR 或设计简报）
- 必要的架构图（至少 C4 Level 2）
- 接口定义或 API 设计
- 已识别的风险和权衡
- 建议至少提前 2 个工作日发给评审者

### 3.2 评审者准备
- 阅读设计文档
- 准备问题和反馈
- 了解相关背景和约束

## 4. 评审检查清单

### 4.1 需求满足
- [ ] 设计是否覆盖所有功能需求
- [ ] 非功能需求（性能、安全、可用性）是否满足
- [ ] 边界条件和异常流程是否处理

### 4.2 架构合理性
- [ ] 是否遵循已有架构原则和模式
- [ ] 组件职责划分是否清晰
- [ ] 依赖方向是否合理（避免循环依赖）
- [ ] 是否考虑了可扩展性和可维护性

### 4.3 接口设计
- [ ] 接口是否清晰、一致
- [ ] 是否遵循 API 设计规范
- [ ] 是否向后兼容
- [ ] 错误处理是否完善

### 4.4 数据设计
- [ ] 数据模型是否合理
- [ ] 数据一致性是否有保障
- [ ] 数据量增长是否考虑
- [ ] 是否有备份和恢复方案

### 4.5 安全性
- [ ] 认证和授权是否完善
- [ ] 敏感数据是否加密
- [ ] 输入是否校验
- [ ] 是否考虑了常见攻击向量

### 4.6 可观测性
- [ ] 关键路径是否有日志和指标
- [ ] 是否可追踪（Tracing）
- [ ] 是否有告警设计
- [ ] 故障是否可诊断

### 4.7 部署与运维
- [ ] 部署策略是否合理
- [ ] 是否有回滚方案
- [ ] 配置变更是否安全
- [ ] 依赖服务是否有降级方案

## 5. 评审会议

### 5.1 参与者
- **作者**：介绍设计方案
- **评审者**（2-4 人）：领域专家、架构师、相关团队
- **记录员**：记录讨论要点和行动项

### 5.2 会议流程
1. 作者介绍设计方案（15-20 分钟）
2. 评审者提问和讨论（20-30 分钟）
3. 总结行动项（5-10 分钟）

### 5.3 会议时长
- 控制在 45-60 分钟内
- 如需更多时间，说明设计可能需要拆分

## 6. 评审输出

### 6.1 评审结论
- **通过**：设计满足要求，可进入实施
- **有条件通过**：需修改后自审即可，无需再次评审
- **需修改后重新评审**：存在重大问题，修改后需再次评审
- **否决**：设计方向有根本问题，需要重新设计

### 6.2 评审记录
```markdown
# 设计评审记录

- 设计文档：[链接]
- 评审日期：YYYY-MM-DD
- 参与者：[姓名列表]
- 评审结论：[通过/有条件通过/需重新评审/否决]

## 关键讨论点
1. [讨论点和结论]
2. [讨论点和结论]

## 行动项
- [ ] [行动项] — 负责人：@xxx，截止：YYYY-MM-DD
- [ ] [行动项] — 负责人：@xxx，截止：YYYY-MM-DD
```

## 7. 验证重点

- 重大设计是否经过评审
- 评审是否使用检查清单
- 评审是否有记录和行动项
- 行动项是否有负责人和截止日期
- 评审结论是否明确
