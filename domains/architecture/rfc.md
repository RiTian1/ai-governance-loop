# RFC（Request for Comments）流程

## 1. RFC 定义

RFC 是一种用于讨论和审批重大技术变更的正式文档流程。相比 ADR 记录决策结果，RFC 强调决策过程中的协作讨论。

### 1.1 RFC 与 ADR 的关系
- RFC 用于变更前的提案与讨论
- ADR 用于记录最终决策结果
- 重大变更：先写 RFC → 讨论通过 → 再写 ADR
- 小型决策：可直接写 ADR，无需 RFC

## 2. 何时需要 RFC

以下情况应启动 RFC 流程：
- 影响多个团队的架构变更
- 引入新技术栈或替换现有技术
- 改变系统间的通信协议
- 数据模型重大重构
- 安全策略变更
- 影响用户体验的重大调整
- 预计工作量超过 2 周的技术方案

不需要 RFC 的情况：
- Bug 修复
- 小型功能迭代
- 团队内部的重构（不影响外部接口）
- 依赖版本升级

## 3. RFC 模板

```markdown
# RFC-[编号]: [提案标题]

## 元数据
- 作者：[姓名]
- 状态：[草稿 | 评审中 | 已接受 | 已拒绝 | 已撤回]
- 创建日期：YYYY-MM-DD
- 评审截止：YYYY-MM-DD
- 关联 ADR：[ADR 编号，待定]

## 摘要
[2-3 句话概述提案内容和目的]

## 动机
[为什么需要这个变更？当前有什么问题？]

## 设计方案
### 方案概述
[详细描述提案的技术方案]

### 架构图
[附带 C4 或其他架构图]

### 接口设计
[API 接口、数据结构、配置格式]

### 数据迁移
[如果涉及数据变更，描述迁移计划]

## 替代方案
### 方案 B：[名称]
[描述和对比]

### 方案 C：[名称]
[描述和对比]

### 方案对比
| 维度 | 方案 A（推荐） | 方案 B | 方案 C |
|------|--------------|--------|--------|
| 开发成本 | 中 | 低 | 高 |
| 维护成本 | 低 | 中 | 低 |
| 性能 | 高 | 中 | 高 |
| 复杂度 | 中 | 低 | 高 |

## 风险与缓解
| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| ... | 高/中/低 | 高/中/低 | ... |

## 实施计划
### 阶段 1：[名称]（预计 X 天）
- [ ] 任务 1
- [ ] 任务 2

### 阶段 2：[名称]（预计 X 天）
- [ ] 任务 3
- [ ] 任务 4

## 回滚计划
[如果实施失败，如何回滚]

## 未解决问题
[列出需要进一步讨论的问题]

---
## 评审意见
[评审者在此添加意见]
```

## 4. RFC 流程

### 4.1 起草
- 作者使用标准模板创建 RFC
- 完善技术方案和替代方案分析
- 状态设置为"草稿"
- 可与少数人先行非正式讨论

### 4.2 提交评审
- 状态改为"评审中"
- 创建 PR 并指定评审者
- 评审者应包含：架构师、相关团队 Lead、安全工程师（如涉及）
- 评审周期：通常 3-7 个工作日

### 4.3 讨论
- 评审者在 PR 中提出意见
- 作者回复和修改 RFC
- 必要时召开线下讨论会
- 记录关键讨论点和决策

### 4.4 决策
- 所有评审者同意 → 状态改为"已接受"
- 被否决 → 状态改为"已拒绝"，记录原因
- 作者主动撤回 → 状态改为"已撤回"
- 创建对应的 ADR 记录决策

### 4.5 实施
- 按照 RFC 中的实施计划执行
- 实施过程中重大偏差应更新 RFC
- 实施完成后在 RFC 中标注完成状态

## 5. 命名与编号

- 文件名格式：`RFC-[编号]-[短标题].md`
- 编号：4 位数字，从 0001 递增
- 示例：`RFC-0001-migrate-to-event-driven-architecture.md`

## 6. 存储位置

```
docs/architecture/rfc/
├── RFC-0001-migrate-to-event-driven-architecture.md
├── RFC-0002-introduce-graphql-gateway.md
└── README.md  # RFC 索引
```

## 7. 验证重点

- 重大技术变更是否有 RFC
- RFC 是否使用标准模板
- 是否包含替代方案和对比分析
- 是否经过评审并记录评审意见
- 是否有实施计划和回滚计划
