# 测试数据管理约束

## 1. 工厂模式

- 测试数据应通过 Factory 或 Builder 模式程序化生成，禁止在测试代码中硬编码大段数据。
- 数据工厂必须支持默认值覆盖，允许测试仅指定与场景相关的字段。
- 共享的数据工厂应集中管理在专用目录（如 `tests/factories/`），禁止分散定义。
- 工厂生成的数据必须满足被测系统的数据校验规则，避免因无效数据导致误报。
- 复杂对象图的构建应通过组合多个工厂完成，禁止在单个工厂中硬编码所有关联关系。

## 2. Fixture 管理

- Fixture 文件必须使用描述性命名，格式为 `<场景>_<数据类型>.<扩展名>`（如 `valid_order_payload.json`）。
- 所有 Fixture 文件必须纳入版本控制，禁止通过 `.gitignore` 排除。
- 废弃的 Fixture 必须及时清理，每次重大重构后应检查 Fixture 的有效性。
- Fixture 文件应包含注释或配套文档说明其适用场景和数据结构。
- 大型 Fixture（超过 500 行）应拆分为可组合的小文件。

## 3. 敏感数据脱敏

- 测试数据中禁止包含真实的个人身份信息（PII）、API 密钥、密码或访问令牌。
- 必须使用脱敏工具或占位符生成器替代真实敏感数据。
- CI 环境中的测试凭证必须通过密钥管理服务注入，禁止明文存储在代码仓库中。
- 从生产环境导出的测试数据必须经过完整脱敏处理后方可使用。
- 代码审查时应检查测试数据是否包含敏感信息，发现即阻断合并。

## 4. 种子可控

- 涉及随机数据的测试必须支持通过固定种子（Seed）重现完全相同的结果。
- 随机种子值必须在测试失败日志中输出，便于快速重现问题。
- 默认应使用固定种子运行测试，仅在专门的模糊测试（Fuzz Testing）中使用随机种子。
- 种子管理方式应在测试框架配置中统一定义，禁止各测试自行管理。
- 基于随机数据的测试失败后，必须先用相同种子重现，确认非 Flaky 后再修复。

## 5. 测试数据库隔离

- 每个测试用例应在独立事务中运行，测试结束后自动回滚，保证数据隔离。
- 若无法使用事务隔离，应为每个测试分配独立的数据库实例或 Schema。
- 禁止多个测试共享可变的数据库状态，避免因执行顺序导致结果不一致。
- 数据库迁移脚本必须在测试环境中自动执行，保证 Schema 与代码版本一致。
- 测试结束后不应残留脏数据，CI 环境中应定期验证数据库清理的完整性。

## 6. 大数据集策略

- 日常功能测试应使用精简数据集（数百条记录），确保测试快速执行。
- 性能测试和压力测试应使用生产级数据集，数据量需在测试计划中明确定义。
- 大数据集应存储在独立的测试数据仓库中，禁止提交到主代码仓库。
- 数据集版本应与测试代码版本对应，避免数据与代码不匹配导致的误判。
- 大数据集的加载应支持增量和并行加载，避免测试启动时间过长。

## 7. 验证重点

- 测试数据是否通过工厂模式生成而非硬编码
- Fixture 文件是否命名规范、及时清理
- 是否存在敏感数据泄露风险
- 随机测试是否可通过固定种子重现
- 数据库测试是否真正隔离
