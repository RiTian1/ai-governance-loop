# 测试证据约束

## 1. 证据格式

- 测试报告必须以结构化格式输出，优先使用 JUnit XML、JSON 或与 CI 系统兼容的标准格式。
- 报告中必须包含：测试名称、执行结果（通过/失败/跳过）、执行耗时和失败原因。
- 纯文本日志仅作为补充，不得作为唯一的测试证据形式。
- 报告解析脚本应纳入版本控制，确保团队成员可统一处理证据。
- 自定义报告格式必须提供对应的 Schema 定义文件，保证可机器验证。

## 2. 截图策略

- UI 测试失败时必须自动捕获当前页面截图，截图应在断言失败点触发。
- 截图文件命名必须包含时间戳和用例名称，格式如 `<用例名>_<时间戳>.png`。
- 截图应与测试报告关联，报告中包含截图的相对路径或可访问链接。
- 成功的 UI 测试不应默认截图，避免存储资源浪费（可通过配置启用）。
- 截图分辨率应与实际测试视口一致，禁止截取缩放或裁剪后的图像。

## 3. 日志采集

- 测试失败时必须自动采集被测系统的相关日志（应用日志、错误日志、请求日志）。
- 日志采集范围应限定为测试执行期间（开始时间至失败时间），避免无关噪声。
- 应保留最近 N 次（建议 10 次）运行的完整日志，超出部分自动归档或清理。
- 日志中的敏感信息（密钥、令牌、密码）必须在采集时自动脱敏。
- 日志文件应按运行批次组织，目录结构为 `<日期>/<运行ID>/<测试名>/`。

## 4. 可重现性要求

- 每份测试证据必须附带完整的执行命令，第三方可据此重现相同的测试结果。
- 证据中必须记录执行环境信息：操作系统、运行时版本、关键依赖版本。
- 使用容器化环境的测试应记录镜像标签或 Dockerfile 哈希值。
- 证据中应包含代码版本标识（Git 提交哈希），确保可追溯到精确的代码状态。
- 环境差异导致的结果不一致应在证据中明确标注并说明原因。

## 5. 归档规则

- 测试证据的默认保留期限为 90 天，关键发布版本的证据应永久保留。
- 证据存储位置必须在项目配置中明确定义，禁止分散存储在个人目录。
- 每份归档证据必须关联到对应的变更标识（变更编号、提交哈希或发布版本号）。
- 归档证据应支持按变更、时间范围或测试套件进行检索。
- 归档操作应自动化执行，禁止依赖人工手动搬运文件。

## 6. 与验证政策的对齐

- 证据优先级应遵循 `04-verification-policy.md` 的定义：结构化自动化输出 > 可复现日志 > 人工记录 > 临时截图 > 口头描述。
- 仅提供低优先级证据时，必须说明无法获取高优先级证据的原因。
- 降级验证场景（如缺少自动化输出、仅有人工结论）必须在证据中显式标注。
- 证据的完整性应作为变更归档（Archive）的前置检查项。
- 定期审计证据质量，确保团队不会逐渐滑向仅依赖低优先级证据的惯性。

## 7. 验证重点

- 测试报告是否为结构化格式且可机器解析
- 失败用例是否附带截图、日志和执行命令
- 证据是否可追溯到具体的代码版本和变更
- 归档证据是否在保留期限内可检索
