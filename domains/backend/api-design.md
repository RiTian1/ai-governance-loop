# API 设计约束

## 1. 适用范围

适用于所有对外暴露的 HTTP/REST API，包括面向前端、移动端、第三方集成的接口。

## 2. RESTful 约定

- 资源命名使用复数名词（如 `/users`、`/orders`），禁止使用动词作为路径。
- HTTP 方法严格对应语义：GET 查询、POST 创建、PUT 全量更新、PATCH 部分更新、DELETE 删除。
- 状态码使用必须准确：200 成功、201 已创建、204 无内容、400 请求错误、401 未认证、403 无权限、404 未找到、409 冲突、422 参数校验失败、429 限流、500 服务端错误。
- 嵌套资源路径不超过两层（如 `/users/{id}/orders`），更深层级使用查询参数替代。
- 所有端点必须在 OpenAPI/Swagger 文档中注册，未注册的端点视为非法。

## 3. API 版本管理

- 推荐使用 URL 路径版本（如 `/v1/users`），语义清晰且缓存友好。
- 同一时间最多维护两个活跃版本，旧版本必须设置明确的废弃时间线。
- 版本升级时必须提供迁移指南，破坏性变更必须在变更日志中标注。
- Header 版本（`Accept: application/vnd.api+json;version=2`）作为备选方案，不作为默认策略。
- 禁止通过查询参数传递版本号（如 `?version=2`），避免缓存污染。

## 4. 幂等性要求

- GET、PUT、DELETE 操作必须天然幂等。
- POST 操作必须通过幂等键（Idempotency-Key）实现幂等性，防止重复提交。
- 幂等键的有效期不低于 24 小时，过期后允许重新提交。
- 幂等性校验失败时返回 409 状态码，并附带原始请求的处理结果。
- 所有写操作的幂等性设计必须在接口文档中明确说明。

## 5. 限流与熔断

- 所有公开 API 必须配置速率限制，默认上限根据业务场景评估后设定。
- 限流响应必须包含 `Retry-After` 头，告知客户端重试时间。
- 熔断阈值：连续失败率超过 50% 或 P99 延迟超过阈值时触发熔断。
- 熔断期间返回 503 状态码，附带降级响应或缓存数据。
- 内部服务间调用同样需要限流保护，防止级联故障。

## 6. 分页与过滤

- 列表接口必须支持分页，禁止一次性返回全量数据。
- 推荐使用游标分页（cursor-based），数据量大或有实时写入时禁止使用偏移分页。
- 默认页大小 20，最大页大小 100，超出范围自动截断并在响应中说明。
- 排序字段必须在允许列表内，禁止接受任意字段排序以防止性能问题。
- 过滤参数使用查询字符串传递，复杂过滤条件使用 POST + 请求体。

## 7. 请求/响应规范

- 统一响应体结构：`{ "code": 0, "message": "ok", "data": {}, "trace_id": "" }`。
- 错误响应结构：`{ "code": 40001, "message": "描述", "details": [], "trace_id": "" }`。
- 时间戳统一使用 ISO 8601 格式（`2024-01-01T00:00:00Z`），时区为 UTC。
- 金额字段使用字符串或最小单位整数表示，禁止使用浮点数。
- 请求体大小限制默认 1MB，文件上传接口单独配置并明确上限。

## 8. 验证重点

- 接口命名是否符合 RESTful 约定
- 版本管理策略是否一致
- 幂等性设计是否覆盖所有写操作
- 限流配置是否合理且有降级方案
- 响应格式是否统一且包含追踪信息
