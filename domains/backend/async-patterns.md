# 异步模式约束

## 1. 适用范围

适用于后端服务中所有异步处理场景，包括消息队列、事件驱动、后台任务、定时调度等。

## 2. 消息队列选择与约束

- 明确消息投递语义：at-least-once（至少一次）为默认选择，消费端必须实现幂等。
- at-most-once（至多一次）仅用于可丢失的通知类消息（如非关键日志采集）。
- exactly-once（恰好一次）语义通过"at-least-once + 消费端去重"实现，不依赖中间件保证。
- 消息体大小限制默认 256KB，超大消息使用"引用模式"（消息体存对象存储，队列传引用）。
- 生产端必须实现发送确认机制，消息发送失败时进入本地重试队列或持久化补偿表。

## 3. 事件驱动架构

- 事件命名采用"领域.实体.动作"格式（如 `order.payment.completed`），全小写，点号分隔。
- 事件 Schema 必须版本化管理，使用语义化版本号（如 v1、v2），禁止破坏性变更。
- 事件溯源（Event Sourcing）场景中，事件流作为唯一事实源，禁止绕过事件流直接修改状态。
- 事件发布必须在业务事务提交后执行，禁止在事务中间发布事件导致不一致。
- 事件消费者必须处理乱序和重复投递，禁止假设事件按序到达。

## 4. 最终一致性

- 跨服务的数据一致性优先使用 Saga 模式，每个步骤必须定义对应的补偿操作。
- Saga 编排模式（Orchestration）适用于流程明确的场景；协作模式（Choreography）适用于松耦合场景。
- 补偿事务必须是幂等的，且必须在设计阶段明确定义，禁止上线后补充。
- 超时处理：每个 Saga 步骤必须设置超时阈值，超时后触发补偿或人工介入。
- 最终一致性的不一致窗口必须在 SLA 中明确定义，并向业务方透明。

## 5. 死信处理

- 所有消息队列必须配置死信队列（DLQ），消费失败超过重试次数后转入 DLQ。
- 默认重试次数 3 次，重试间隔使用指数退避（1s → 2s → 4s）。
- DLQ 中的消息必须保留至少 7 天，供排查和重新投递使用。
- 必须建立 DLQ 监控告警，DLQ 积压超过阈值时触发告警并通知值班人员。
- 提供人工干预工具：支持查看、重投、丢弃 DLQ 中的消息，操作必须有审计日志。

## 6. 异步任务生命周期

- 任务状态机：提交（pending）→ 执行中（running）→ 成功（completed）/ 失败（failed）→ 补偿（compensating）/ 重试（retrying）。
- 所有异步任务必须支持状态查询，调用方可随时获取任务当前状态。
- 任务执行超时必须设置上限，超时后标记为失败并触发告警。
- 失败任务的重试必须有最大次数限制，超过限制后进入人工处理队列。
- 任务状态变更必须记录日志，包含任务 ID、状态、时间戳、执行节点信息。

## 7. 背压管理

- 消费者处理速率低于生产速率时，必须有背压机制防止队列无限膨胀。
- 队列深度告警：队列积压超过阈值（根据业务评估）时触发告警。
- 消费速率控制：支持动态调整消费者并发数，根据队列深度自动扩缩。
- 生产端限流：当下游消费能力不足时，生产端必须具备限流或缓冲能力。
- 背压传播：多级队列架构中，下游背压必须能传播到上游，禁止中间层无限缓冲。

## 8. 验证重点

- 消息投递语义是否与业务需求匹配
- 事件 Schema 是否版本化且无破坏性变更
- Saga 每个步骤是否都有对应的幂等补偿操作
- 死信队列是否配置且有监控告警
- 背压机制是否覆盖所有异步处理链路
