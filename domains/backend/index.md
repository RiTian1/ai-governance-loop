# 后端领域约束

## 1. 适用范围

适用于服务端、应用服务、任务调度、副作用执行链、后台处理逻辑。
涵盖 API 接入、业务编排、领域建模、基础设施对接等全链路后端场景。

## 2. 默认原则

- 应用服务负责用例编排，不直接承载底层资源细节。
- 领域规则与基础设施细节分离。
- 高风险副作用通过共享校验、策略、执行桥接边界进入。
- 服务间通信优先使用显式契约，禁止隐式耦合。
- 所有对外暴露的接口必须具备版本管理能力。

## 3. 边界约束

- API 层不直接吞掉领域规则与存储规则。
- 脚本、管理入口、AI 提案入口不直接绕过服务层写入不可逆状态。
- 长耗时任务优先异步化、后台化、可恢复化。
- 跨服务调用必须设置超时与重试上限，禁止无限等待。
- 外部依赖（第三方 API、中间件）必须通过适配层隔离。

## 4. 服务分层模型

| 层级 | 职责 | 约束 |
|------|------|------|
| 接入层 | 协议解析、认证鉴权、限流熔断 | 不包含业务逻辑 |
| 应用层 | 用例编排、事务协调、DTO 转换 | 不直接访问基础设施 |
| 领域层 | 业务规则、实体、值对象、领域事件 | 不依赖任何外部框架 |
| 基础设施层 | 持久化、消息队列、外部服务适配 | 仅实现领域层定义的接口 |

## 5. 健康检查要求

- 所有服务必须实现 readiness probe（就绪探针），确认依赖资源可用后才接收流量。
- 所有服务必须实现 liveness probe（存活探针），检测进程死锁或不可恢复状态。
- 探针端点禁止包含重量级检查，响应时间应低于 200ms。
- 健康检查失败时必须返回明确的失败原因，便于运维排查。

## 7. 验证重点

- 用例边界是否清晰
- 错误处理与回滚路径是否明确
- 副作用是否可审计、可追踪、可验证
- 分层是否严格遵守依赖方向（上层依赖下层，禁止反向）
- 健康检查端点是否覆盖所有关键依赖
