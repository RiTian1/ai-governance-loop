# 配置分层策略

## 1. 分层模型

### 1.1 三层配置模型
```
┌─ 运行时配置（Runtime）── 环境变量、命令行参数、远程配置中心
│  优先级最高，覆盖下层所有值
│
├─ 环境配置（Environment）── config.{env}.yaml
│  环境特定的差异化配置
│
└─ 基础配置（Base）── config.base.yaml
   默认值，所有环境共享的通用配置
```

### 1.2 优先级规则
从高到低：
1. **运行时注入**（环境变量、命令行参数）
2. **远程配置中心**（Consul, etcd, Apollo, Nacos）
3. **环境配置文件**（config.prod.yaml）
4. **基础配置文件**（config.base.yaml）
5. **代码中的硬编码默认值**（最低优先级）

## 2. 文件组织

### 2.1 目录结构
```
config/
├── config.base.yaml          # 基础配置
├── config.dev.yaml            # 开发环境
├── config.test.yaml           # 测试环境
├── config.staging.yaml        # 预发布环境
├── config.prod.yaml           # 生产环境
├── config.schema.json         # 配置 Schema
└── config.example.yaml        # 配置模板
```

### 2.2 命名约定
- 基础配置：`config.base.[ext]` 或 `config.default.[ext]`
- 环境配置：`config.[env].[ext]`
- 本地覆盖：`config.local.[ext]`（必须加入 .gitignore）
- 配置模板：`config.example.[ext]`

### 2.3 版本控制规则
- 基础配置和环境配置模板应纳入版本控制
- 本地覆盖文件（config.local.*）不得纳入版本控制
- 生产环境的敏感值不得纳入版本控制

## 3. 合并策略

### 3.1 深度合并
- 环境配置应深度合并（Deep Merge）到基础配置
- 数组类型应采用替换策略（非追加），避免歧义
- 合并后的最终配置应可输出用于调试

### 3.2 变更影响分析
- 修改基础配置前应评估对所有环境的影响
- 修改环境配置应验证与基础配置的兼容性
- 配置变更应有 Diff 预览机制

## 4. 远程配置中心

### 4.1 适用场景
- 需要运行时动态调整的配置
- 跨服务共享的配置
- 需要灰度发布的配置

### 4.2 治理要求
- 远程配置变更应有审批流程
- 远程配置应有版本历史和回滚能力
- 远程配置应有变更通知机制
- 远程配置应有访问控制

## 5. 验证重点

- 是否遵循三层配置模型
- 基础配置和环境配置是否正确分离
- 本地覆盖文件是否在 .gitignore 中
- 配置合并是否使用深度合并策略
- 远程配置是否有审批和回滚机制
