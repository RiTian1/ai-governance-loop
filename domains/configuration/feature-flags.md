# 特性开关标准

## 1. 特性开关分类

### 1.1 发布开关（Release Toggles）
- **用途**：控制未完成功能的可见性，支持 trunk-based 开发
- **生命周期**：短期（days-weeks），功能发布后应移除
- **示例**：`FEATURE_NEW_CHECKOUT_PAGE_ENABLED`

### 1.2 运维开关（Ops Toggles）
- **用途**：运行时控制系统行为（降级、限流、开关）
- **生命周期**：长期，可能永久保留
- **示例**：`OPS_CIRCUIT_BREAKER_ENABLED`, `OPS_RATE_LIMIT_THRESHOLD`

### 1.3 实验开关（Experiment Toggles）
- **用途**：A/B 测试、灰度实验
- **生命周期**：中期（weeks-months），实验结束后移除
- **示例**：`EXPERIMENT_NEW_PRICING_VARIANT`

### 1.4 权限开关（Permission Toggles）
- **用途**：基于用户/角色控制功能访问
- **生命周期**：长期
- **示例**：`PREMIUM_ANALYTICS_ENABLED`

## 2. 命名规范

- 开关名称格式：`[类型前缀]_[功能描述]_[动作]`
- 类型前缀：`FEATURE_`, `OPS_`, `EXPERIMENT_`, `PERM_`
- 功能描述使用 UPPER_SNAKE_CASE
- 布尔开关以 `_ENABLED` 或 `_ACTIVE` 结尾
- 阈值开关以 `_THRESHOLD` 或 `_LIMIT` 结尾

## 3. 生命周期管理

### 3.1 创建
- 创建开关时必须记录：创建日期、负责人、预期移除日期、用途说明
- 开关定义应集中管理（配置文件或开关管理平台）
- 新开关应默认关闭（fail-safe）

### 3.2 使用
- 代码中使用开关应有统一的检查接口（如 `featureFlags.isEnabled('...')`)
- 禁止使用嵌套或组合开关（if A && B && !C），应合并为单一开关
- 开关分支应有完整的测试覆盖（开/关两种状态）

### 3.3 清理
- 发布开关在功能正式发布后 2 周内必须移除
- 实验开关在实验结束后 1 周内必须移除
- 应定期扫描过期未清理的开关，生成清理报告
- 清理时应移除所有相关代码路径、测试和配置

## 4. 技术实现

### 4.1 存储方式
- 简单项目：配置文件（JSON/YAML）
- 中等项目：远程配置中心（Consul, etcd）
- 大型项目：专用开关平台（LaunchDarkly, Unleash, Flagsmith）

### 4.2 运行时评估
- 开关状态应支持运行时动态更新（无需重启）
- 实验开关应支持基于用户属性的定向分组
- 开关评估应有缓存机制，避免频繁远程查询

## 5. 监控与审计

- 所有开关变更必须记录审计日志
- 应监控开关的使用频率和影响范围
- 应设置告警：过期未清理的开关
- 应定期生成开关清单报告

## 6. 验证重点

- 开关命名是否符合规范
- 是否记录了创建日期和预期移除日期
- 过期开关是否及时清理
- 开关分支是否有测试覆盖
- 是否有审计日志和监控
