# 部署模式与回滚策略

## 1. 部署模式选择

### 1.1 蓝绿部署（Blue-Green Deployment）
**适用场景**：
- 需要快速回滚能力
- 可以承受双倍资源成本
- 数据库 Schema 向后兼容

**实施要点**：
- 维护两套完全相同的环境（蓝/绿）
- 新版本部署到非活跃环境
- 通过负载均衡器切换流量
- 切换应在秒级完成
- 旧版本环境保留一段时间（如 24 小时）以便回滚

**验证要求**：
- 切换前必须验证新环境健康状态
- 切换后必须监控错误率和性能指标
- 数据库迁移必须向后兼容

### 1.2 金丝雀部署（Canary Deployment）
**适用场景**：
- 需要渐进式验证
- 用户基数大，可分流小比例流量
- 风险较高的变更

**实施要点**：
- 先部署到小比例节点（如 5%）
- 监控关键指标（错误率、延迟、业务指标）
- 逐步扩大流量比例（5% → 25% → 50% → 100%）
- 每个阶段设置观察期（如 30 分钟）
- 发现异常立即回滚

**验证要求**：
- 必须定义金丝雀成功标准（如错误率 < 0.1%）
- 必须配置自动回滚触发条件
- 必须有流量分流机制（基于用户 ID、地域等）

### 1.3 滚动部署（Rolling Deployment）
**适用场景**：
- 资源受限，无法维护双倍环境
- 服务无状态或状态可迁移
- 可接受短暂的版本混合状态

**实施要点**：
- 逐个或分批替换节点
- 每批替换后验证健康状态
- 保持最小可用节点数（如 N-1）
- 替换过程中新旧版本共存

**验证要求**：
- 新旧版本必须兼容（API、数据格式）
- 必须配置健康检查
- 必须设置替换失败的回滚策略

### 1.4 重建部署（Recreate Deployment）
**适用场景**：
- 开发/测试环境
- 单体应用且可接受停机
- 新旧版本不兼容

**实施要点**：
- 停止旧版本
- 部署新版本
- 启动新版本

**限制**：
- 不得用于生产环境（除非有维护窗口）
- 必须提前通知用户停机时间

## 2. 回滚策略

### 2.1 回滚触发条件
以下情况应立即触发回滚：
- 错误率超过基线阈值（如 5 倍）
- 关键业务指标异常（如支付成功率下降）
- 性能严重劣化（如 P99 延迟超过 SLO）
- 安全漏洞被利用
- 数据一致性问题

### 2.2 回滚类型

**应用回滚**：
- 回滚到上一个稳定版本
- 应在 5 分钟内完成
- 应自动化执行

**数据库回滚**：
- 仅回滚 Schema 变更（如果支持）
- 数据回滚需谨慎评估（可能导致数据丢失）
- 应有数据备份和恢复预案

**配置回滚**：
- 回滚配置变更
- 应通过配置管理系统（如 Consul, etcd）
- 应立即生效

### 2.3 回滚验证
回滚后必须验证：
- 服务健康状态恢复
- 错误率降至正常水平
- 关键业务流程可用
- 数据一致性完整

### 2.4 回滚后处理
- 记录回滚原因和时间
- 分析根因（RCA）
- 修复问题后重新部署
- 更新部署检查清单

## 3. 部署自动化

- 所有部署应通过 CI/CD 流水线执行，禁止手动部署。
- 部署脚本应幂等：多次执行结果一致。
- 部署应有详细日志，记录每个步骤的执行状态。
- 部署应支持 Dry-Run 模式，预览变更而不实际执行。

## 4. 部署窗口管理

- 生产环境应定义部署窗口（如工作日 10:00-16:00）。
- 禁止在高峰时段或节假日部署（除紧急热修复）。
- 部署窗口外的部署需要特殊审批。
- 部署窗口应考虑用户时区和业务高峰期。

## 5. 验证重点

- 是否选择了合适的部署模式
- 是否定义了明确的回滚触发条件
- 回滚是否自动化且可在 5 分钟内完成
- 部署是否通过 CI/CD 流水线执行
- 是否定义了部署窗口并严格执行
