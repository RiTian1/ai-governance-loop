# 环境分层与准入策略

## 1. 环境分层定义

### 1.1 标准环境层级
项目应至少包含以下环境：
- **开发环境（Dev）**：开发人员日常开发和调试
- **测试环境（Test/QA）**：功能测试、集成测试
- **预发布环境（Staging/Pre-Prod）**：生产环境镜像，用于最终验证
- **生产环境（Prod）**：面向真实用户的生产系统

### 1.2 可选环境
根据项目需要可增加：
- **沙箱环境（Sandbox）**：实验性功能验证
- **演示环境（Demo）**：客户演示或销售展示
- **灾备环境（DR）**：灾难恢复备用环境

## 2. 环境准入规则

### 2.1 开发环境（Dev）
- 准入条件：代码编译通过、单元测试通过
- 部署频率：按需部署，可多次/天
- 数据要求：使用模拟数据或脱敏数据
- 访问控制：开发团队可访问

### 2.2 测试环境（Test/QA）
- 准入条件：通过 Dev 环境验证、集成测试通过
- 部署频率：每日或每次 PR 合并后
- 数据要求：使用测试数据集，接近生产数据结构
- 访问控制：开发团队 + QA 团队可访问

### 2.3 预发布环境（Staging）
- 准入条件：通过所有自动化测试、代码审查通过、安全扫描通过
- 部署频率：每次发布前
- 数据要求：使用生产数据镜像（脱敏）或高保真模拟数据
- 访问控制：开发团队 + QA + 产品经理可访问
- 配置要求：与生产环境配置一致（除敏感凭据外）

### 2.4 生产环境（Prod）
- 准入条件：通过 Staging 验证、人工审批、变更窗口检查
- 部署频率：按发布计划（如每周、每两周）
- 数据要求：真实生产数据
- 访问控制：仅运维团队和授权人员可访问
- 变更管理：所有变更必须有变更单（Change Request）

## 3. 环境配置隔离

### 3.1 配置分层
- 配置应分为：基础配置（base）+ 环境特定配置（env-specific）
- 环境特定配置应覆盖基础配置，不得修改基础配置
- 配置文件命名约定：`config.base.yaml`, `config.dev.yaml`, `config.prod.yaml`

### 3.2 密钥管理
- 开发环境可使用占位符密钥或本地密钥
- 测试/预发布环境应使用专用测试密钥
- 生产环境密钥必须使用密钥管理服务（Vault, AWS Secrets Manager, Azure Key Vault）
- 禁止在代码或配置文件中硬编码生产密钥

### 3.3 资源隔离
- 不同环境应使用独立的资源（数据库、缓存、消息队列）
- 生产环境资源不得与其他环境共享
- 环境间应有网络隔离（VPC, 子网, 安全组）

## 4. 环境一致性

### 4.1 基础设施一致性
- 所有环境应使用相同的基础设施代码（IaC）
- 环境差异应通过参数化配置，而非不同的 IaC 代码
- 预发布环境应尽可能镜像生产环境（配置、规模、拓扑）

### 4.2 部署流程一致性
- 所有环境应使用相同的部署脚本和流程
- 部署步骤应自动化且幂等
- 部署应可回滚，回滚流程应定期演练

## 5. 环境监控与审计

### 5.1 监控要求
- 所有环境应配置基础监控（CPU, 内存, 磁盘, 网络）
- 生产和预发布环境应配置应用级监控（日志, 指标, 追踪）
- 环境健康状态应可视化（Dashboard）

### 5.2 审计要求
- 所有环境的部署操作应记录审计日志
- 生产环境的访问和变更应有完整审计轨迹
- 审计日志应不可篡改且长期保留（至少 1 年）

## 6. 验证重点

- 是否定义了清晰的环境分层
- 每个环境是否有明确的准入条件
- 环境配置是否隔离且版本控制
- 生产密钥是否使用密钥管理服务
- 环境间是否有资源和网络隔离
- 部署流程是否在所有环境保持一致
