# CI/CD 流水线门禁策略

## 1. 门禁分级

### 1.1 阻断级门禁（Blocking Gates）
以下检查失败必须阻断构建，不得合入或发布：
- 编译失败
- 单元测试失败
- 代码覆盖率低于项目基线（建议 ≥ 70%）
- 静态代码分析发现严重缺陷（Critical/High）
- 安全扫描发现高危漏洞（CVSS ≥ 7.0）
- 许可证合规检查失败
- API 契约校验失败（实现与契约不一致）

### 1.2 警告级门禁（Warning Gates）
以下检查失败应发出警告，但不阻断构建：
- 代码风格检查（Linter）警告
- 静态分析中等缺陷（Medium）
- 性能测试结果劣化但未超过阈值
- 文档缺失或过期

### 1.3 信息级门禁（Informational Gates）
以下检查仅记录信息，不影响构建：
- 代码复杂度报告
- 依赖更新提示
- 技术债务统计

## 2. 环境特定门禁

### 2.1 开发环境（Dev）
- 必须通过：编译、单元测试
- 可选：集成测试、代码覆盖率

### 2.2 测试环境（Staging）
- 必须通过：所有阻断级门禁
- 必须通过：集成测试、端到端测试
- 必须通过：性能基线测试

### 2.3 生产环境（Prod）
- 必须通过：所有阻断级门禁
- 必须通过：所有测试（单元、集成、E2E、性能）
- 必须通过：安全扫描（SAST, DAST, SCA）
- 必须通过：人工审批（关键变更）
- 必须通过：变更窗口检查（是否在允许的发布时间窗口内）

## 3. 审批流程

### 3.1 自动审批
以下情况可自动通过审批：
- 依赖版本升级（PATCH 版本）
- 文档更新
- 配置微调（非生产环境）

### 3.2 人工审批
以下情况必须人工审批：
- 生产环境部署
- 数据库 Schema 变更
- 安全相关变更
- 架构重大调整

### 3.3 多人审批
以下情况需要至少 2 人审批：
- MAJOR 版本发布
- 回滚操作
- 紧急热修复（Hotfix）

## 4. 门禁配置管理

- 门禁规则应以代码形式定义（如 `.gitlab-ci.yml`, `Jenkinsfile`, GitHub Actions YAML）。
- 门禁阈值应可配置且版本控制（如覆盖率基线、性能基线）。
- 门禁规则变更应经过 Code Review。
- 禁止在 CI 配置中硬编码密钥或凭据，应使用密钥管理服务。

## 5. 门禁豁免机制

- 紧急情况下可申请门禁豁免，但必须：
  - 记录豁免原因和审批人
  - 在事后补齐缺失的检查
  - 豁免记录应可审计
- 禁止滥用豁免机制，豁免率应监控并定期复盘。

## 6. 验证重点

- CI 配置是否包含所有阻断级门禁
- 门禁阈值是否合理且可配置
- 生产部署是否有人工审批
- 门禁规则是否版本控制
- 是否存在硬编码的密钥或凭据
