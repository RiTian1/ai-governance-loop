# 变更日志与版本记录约束

## 1. 格式规范

- 变更日志必须遵循 [Keep a Changelog](https://keepachangelog.com/) 格式。
- 文件名必须为 `CHANGELOG.md`，置于项目根目录。
- 每个版本条目必须包含版本号和发布日期，格式为 `## [x.y.z] - YYYY-MM-DD`。
- 未发布的变更应记录在 `## [Unreleased]` 区段，发布时移入对应版本号。

## 2. 语义化版本关联

- 版本号必须遵循语义化版本（SemVer）：MAJOR.MINOR.PATCH。
- MAJOR 变更（不兼容的 API 修改）必须在日志中明确标注影响范围和迁移方式。
- PATCH 版本不得包含新功能，仅限缺陷修复和安全补丁。

## 3. 变更类型分类

- 必须使用以下标准分类记录变更：Added（新增）、Changed（变更）、Deprecated（废弃）、Removed（移除）、Fixed（修复）、Security（安全）。
- 禁止使用自定义分类或模糊描述（如"杂项"、"其他"、"优化"）。
- 每条变更记录应包含简要描述和关联的 Issue/PR 编号。

## 4. 自动生成与维护

- 应配置工具从 commit message 或 PR 标题自动汇总变更日志草稿。
- 自动生成的内容必须经人工审核后方可发布，禁止未经审核直接发布自动日志。
- commit message 应遵循 Conventional Commits 规范，确保自动汇总的准确性。

## 5. 发布纪律

- 每次版本发布必须同步更新 CHANGELOG.md，未更新的发布应阻断。
- 不得在 CHANGELOG 中包含内部讨论记录、临时决策或待办事项。
- 不得回溯修改已发布版本的日志条目，如需勘误应在新版本中说明。
- 历史版本日志不得删除，必须完整保留。

## 6. 验证重点

- CHANGELOG.md 是否存在且格式符合 Keep a Changelog
- 版本号是否遵循语义化版本
- 变更分类是否使用标准类型
- 发布版本是否同步更新了日志
- 是否存在未经分类的模糊条目
