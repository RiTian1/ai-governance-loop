# 日志规范

## 1. 结构化日志格式

### 1.1 必须使用结构化日志
- 日志必须以结构化格式输出（JSON 推荐），禁止纯文本日志
- 每条日志必须包含以下基础字段：

```json
{
  "timestamp": "2025-01-15T10:30:00.123Z",
  "level": "INFO",
  "service": "order-service",
  "message": "Order created successfully",
  "trace_id": "abc123def456",
  "span_id": "789ghi",
  "context": {
    "user_id": "u-12345",
    "order_id": "o-67890"
  }
}
```

### 1.2 字段命名规范
- 字段名使用 snake_case
- 时间戳字段名统一为 `timestamp`，格式为 ISO 8601（UTC）
- 级别字段名统一为 `level`
- 服务名字段名统一为 `service`
- 追踪标识字段名统一为 `trace_id`, `span_id`
- 业务上下文统一放入 `context` 对象

## 2. 日志级别

### 2.1 级别定义
| 级别 | 用途 | 示例 |
|------|------|------|
| FATAL | 系统无法继续运行 | 数据库连接池耗尽 |
| ERROR | 操作失败，需要关注 | API 调用返回 500 |
| WARN | 潜在问题，不影响正常运行 | 重试次数接近上限 |
| INFO | 重要业务事件 | 订单创建成功 |
| DEBUG | 开发调试信息 | SQL 查询详情 |
| TRACE | 极细粒度调试 | 函数入参/出参 |

### 2.2 级别使用规则
- 生产环境默认日志级别为 INFO
- DEBUG/TRACE 仅在排查问题时临时开启
- 日志级别应支持运行时动态调整（无需重启）
- 禁止在循环中使用 INFO 及以上级别日志

## 3. 日志脱敏

### 3.1 必须脱敏的字段
- 密码、密钥、Token
- 身份证号、手机号、邮箱地址
- 银行卡号、支付信息
- 健康/医疗数据
- 请求/响应 Body 中的敏感字段

### 3.2 脱敏方式
- 掩码：`138****5678`, `admin@****.com`
- 哈希：适用于需要关联但不需要还原的场景
- 截断：仅保留前/后几位
- 移除：完全不记录

### 3.3 自动脱敏
- 应在日志框架层面配置自动脱敏规则
- 匹配模式：字段名包含 `password`, `secret`, `token`, `key`, `credential`
- 正则匹配：手机号、身份证号、银行卡号等

## 4. 日志输出与存储

### 4.1 输出目标
- 应用日志输出到 stdout/stderr（容器化推荐）
- 由日志收集器（Fluentd, Filebeat, Vector）负责采集和转发
- 禁止应用程序直接写入远程日志系统

### 4.2 存储与保留
- 热数据：最近 7-14 天，支持全文检索
- 温数据：最近 30-90 天，支持按条件查询
- 冷数据：90 天以上，归档存储（合规需要可延长）
- 保留策略应在日志平台中配置并文档化

## 5. 验证重点

- 日志是否使用结构化格式（JSON）
- 是否包含必要的基础字段（timestamp, level, service, trace_id）
- 敏感信息是否脱敏
- 日志级别使用是否合理
- 是否支持运行时动态调整日志级别
