# 证据闭环（`proj.orch.r1` / `r3` / `r4` / `r7`）

## 成功三问（`r1`）

任何一个"成功"都要能回答：

| 问 | 字段 | 答不上会怎样 |
|---|---|---|
| ① 谁产出的 | `producer` / `model_identity` / `operator` | 无法追责，也无法判断能力归属 |
| ② 产出的是什么 | `artifact` + `sha256` | 无法证明"确实改变了什么" |
| ③ 之后有没有变过 | `mtime_ns` / 哈希链 / 漂移检测 | 无法排除"报成功之后又被改坏" |

三问答不上任何一问 → 记 `unverified`，**不是成功**。

## 真值在事件流（`r3`）

统计字段（成功次数、失败次数）只是投影。真值是 append-only 事件流的每一行。

改历史只能改事件，不能改统计字段——否则"统计说 5 次成功，事件里只有 2 条"这种矛盾无法被发现。

事件流必须可校验：

```
seq           必须等于行号
previous_hash 必须等于上一行的 event_hash
event_hash    = sha256(去掉 event_hash 后的规范化 JSON)
```

任一项不通过即拒绝继续（不是"跳过坏行继续跑"）。

## 对账在读侧（`r4`）

对账放在**读取**时做，不放在写入时做。原因：

- 写入侧对账，篡改会被下一次写"洗白"成新基准（launder into the mirror）
- 读取侧对账，被篡改的记录既不会被当成事实下发，也不会被固化

要挡的四种形状：序号倒退、单元丢失、状态被单边改写、权威版本被降级。

## 判不了要显式（`r7`）

| 折叠（错） | 显式（对） |
|---|---|
| 评分失败 → 默认 5.0 分 | `unscored`，且不参与排序 |
| 评审不可用 → 视为通过 | `unchecked`，标记但不放行高风险的 |
| 判定解析不出 → 倒向有利一边 | `unparsed`，不倒向任何一边 |

判据：**"没发生"与"正常"在数据结构上必须长得不一样**。
如果两者都是"空字符串"或"默认值"，系统必然把失败统计成成功。
