# 依赖与供应链安全

## 1. CVE 扫描要求

- CI 流水线必须集成依赖漏洞扫描（如 Snyk、Trivy、npm audit、pip-audit），作为合并门禁。
- 扫描频率：每次 PR 构建必须执行，主分支每日至少执行一次全量扫描。
- 严重等级阈值：Critical 和 High 级别漏洞必须阻断合并，Medium 级别需在迭代内修复。
- 已知无法立即修复的漏洞必须记录豁免理由、负责人和预计修复时间。
- 运行时容器镜像必须在构建和部署阶段分别执行漏洞扫描。

## 2. SBOM 生成和维护

- 每次发布版本必须生成 SBOM（软件物料清单），格式采用 SPDX 或 CycloneDX。
- SBOM 必须包含所有直接依赖和传递依赖的名称、版本、许可证和来源信息。
- SBOM 应作为发布产物的一部分归档，支持事后审计和漏洞追溯。
- 当依赖发生变更时，SBOM 必须同步更新。
- 关键项目应将 SBOM 纳入合规交付物清单。

## 3. 供应链审计

- 依赖安装必须使用锁文件（package-lock.json、poetry.lock、go.sum 等），禁止跳过锁文件安装。
- 锁文件中的依赖哈希必须校验，检测到不一致时阻断构建。
- 包管理器的镜像源必须为可信来源，私有仓库必须启用访问认证。
- 新引入的依赖必须经过安全评估（维护活跃度、已知漏洞、下载量、维护者信誉）。
- 禁止从非官方渠道（个人博客、论坛附件等）下载和引入依赖包。

## 4. 自动升级策略

- 推荐配置 Dependabot 或 Renovate 自动创建依赖升级 PR。
- 自动升级 PR 必须通过完整的 CI 测试套件后方可合并。
- 安全补丁类升级应配置为自动合并（在 CI 通过的前提下）。
- 主版本升级必须人工审查，评估 Breaking Changes 的影响。
- 自动升级工具的配置文件必须纳入版本控制，变更需经过代码审查。

## 5. 许可证合规

- 所有依赖的许可证必须与项目许可证兼容，引入前需确认。
- 禁止引入使用 AGPL、SSPL 等强传染性许可证的依赖（除非项目本身采用相同许可证）。
- 许可证扫描应集成到 CI 流水线，不合规的依赖阻断合并。
- 与 `open-source-compliance` 域联动：许可证合规的详细规则参见该域定义。
- 商业项目必须维护许可证白名单，仅允许白名单内的许可证类型。

## 6. 验证重点

- CI 流水线是否集成依赖漏洞扫描且配置了严重等级门禁
- 是否使用锁文件且校验依赖哈希
- 发布版本是否附带 SBOM
- 自动升级工具是否已配置且安全补丁升级流程畅通
- 依赖许可证是否经过合规检查
