# 安全测试

## 1. SAST 集成要求

- CI 流水线必须集成静态应用安全测试工具（如 Semgrep、SonarQube、CodeQL）。
- SAST 扫描在每次 PR 提交时自动触发，发现高危问题阻断合并。
- SAST 规则集必须覆盖 OWASP Top 10 对应的代码模式。
- 自定义规则应根据项目技术栈和历史漏洞持续补充。
- SAST 扫描的误报应通过标注机制（如 `// nosec` + 理由注释）管理，禁止全局禁用规则。

## 2. DAST 运行约束

- 动态应用安全测试必须在独立的测试环境中执行，禁止在生产环境运行。
- DAST 工具（如 OWASP ZAP、Burp Suite）应在每次发布前的集成测试阶段运行。
- DAST 扫描范围必须覆盖所有对外暴露的 API 端点和 Web 页面。
- 发现的漏洞必须按严重等级分类并录入缺陷跟踪系统。
- DAST 扫描结果应与 SAST 结果关联分析，减少重复报告和误报。

## 3. SCA 与依赖安全联动

- 软件成分分析（SCA）必须与 `dependency-security` 域的 CVE 扫描协同工作。
- SCA 工具应在 CI 流水线中与依赖漏洞扫描共享扫描结果，避免重复扫描。
- SCA 发现的许可证风险应同步报告给合规团队。
- 传递依赖中的已知漏洞必须纳入 SCA 扫描范围。
- SCA 扫描结果应纳入 SBOM 生成流程，补充漏洞状态信息。

## 4. 渗透测试门禁

- 面向外部用户的系统在首次上线前必须完成渗透测试。
- 重大功能变更或架构调整后，必须重新执行针对性渗透测试。
- 渗透测试可由内部安全团队或经认证的第三方执行。
- 与 `pentest-and-vulnerability-research` 域联动：渗透测试的方法论和报告规范参见该域定义。
- 渗透测试发现的所有漏洞必须在约定时限内修复并复测确认。

## 5. 安全回归测试

- 每个安全漏洞修复必须附带对应的回归测试用例，验证漏洞已被修复。
- 回归测试用例必须覆盖原始攻击向量及其变体。
- 安全回归测试纳入 CI 持续运行，确保修复不被后续变更破坏。
- 回归测试用例应标记为安全测试类别，便于独立统计和审计。
- 历史安全漏洞的回归测试用例禁止删除，除非对应功能已完全下线。

## 6. 安全测试覆盖率目标

- 认证、鉴权、输入校验等安全关键路径的测试覆盖率不低于 90%。
- 每个 OWASP Top 10 类别至少有对应的测试用例覆盖。
- 安全测试覆盖率应作为质量门禁指标，纳入 CI 检查。
- 新增的安全敏感功能必须同步提交安全测试用例，否则阻断合并。
- 定期（至少每季度）审查安全测试覆盖率报告，识别薄弱环节。

## 7. 验证重点

- SAST 工具是否已集成到 CI 流水线且覆盖 OWASP Top 10
- DAST 是否在发布前执行且覆盖所有对外端点
- 安全漏洞修复是否均附带回归测试用例
- 安全关键路径的测试覆盖率是否达标
- 渗透测试是否在上线前和重大变更后执行
