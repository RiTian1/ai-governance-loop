# 从 E2E 需求变更看有无治理的效果

## 选取的需求

需求来自现有 `test/e2e/scenarios/*batch_remove*` 这类场景最容易暴露的问题：

- 批量删除接口参数 `ids` 的解析语义发生变化
- 这类变化会同时影响错误处理、去重、空片段、边界输入与 E2E 预期

## 有 Governance 时

agent 更可能把问题建模成：

- 规则语义变化
- 影响现有场景契约
- 必须同时考虑实现、E2E、证据、CI 门禁

因此最终结果通常是：

- 改动范围更完整
- 解释更清楚
- 回归面更稳
- 交付更适合团队复用

## 无 Governance 时

agent 更可能把问题建模成：

- 一个接口容错小改动

因此最终结果通常是：

- 起步更快
- 单点修复更直接
- 但容易漏掉同构场景族、E2E 语义同步和证据整理

## 关键差异

差异不在“会不会写代码”，而在：

- 会不会先识别变更类型
- 会不会自动联想到验证与门禁
- 会不会把新规则沉淀成团队可复用资产
