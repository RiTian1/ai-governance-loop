# Agent RSI 工程基础设施（候选协议）

RSI 在此指 **受约束的递归自改进**：Agent 可以提出改变自己的治理规则、检索、检查点与工具链，但必须通过可复现的对照评测及人工审查后才能晋升。**对话历史由产生它的 CLI 原生 session 记录作为权威来源**；governance 中的摘要、索引和检查点均为派生导航材料，不得覆盖原始对话。此协议先作为试点，不自动改写现行基线。

## 1. 四层状态

1. **权威规则**：Git 中的 manifest、索引、foundations/domains 和 Revision；变更走候选、评审、合并。
2. **项目事实与工作产物**：Story、Change、代码、测试记录、运行环境清单；事实带来源和版本，密钥只记引用。
3. **短期任务状态与对话索引**：目标、已完成、下一步、决策、证据、阻塞和工件引用。CLI 原生 session 是对话真源；governance 的 RSI 域只保存摘要、定位符和来源校验信息。scripts/rsi_checkpoint.py 生成的快照是恢复线索，不替代原始对话或 Git 提交。
4. **观测与评测**：对照任务的通过率、返工、恢复耗时、关键遗漏、输入 token；原始评测数据和判据须留档。

## 对话权威与派生索引

CLI 兼容与恢复顺序见 rsi/native-cli-compatibility.md。压缩和原生 resume 由 CLI 自己管理；治理索引仅在定位来源、跨会话交接或可验证工件出现矛盾时按需读取。

- Cursor、Codex 等 CLI 自己保存和回溯的 session 是对话真源。governance 的 rsi/ 域只保存短摘要、任务 ID、原生 session ID、机器、定位器和锚点；不复制全量聊天，不替代 CLI 回溯。
- Agent 在阶段边界总结索引；重要决策的真实性或上下文发生争议时，按定位器打开 CLI 原文核对。若原会话离线、被清理或本机无权限，索引必须表明来源不可核实。
- 任务检查点与对话索引分开：检查点用于当下续跑，索引用于跨会话发现来源。任一派生记录都不成为原对话的权威副本。
- 用 scripts/rsi_session_index.py add/search/locate 录入、检索和定位。录入必须传 CLI 原生 session ID 与机器标识；若可读取原生 session 文件，脚本只计算 SHA-256，不复制原文。未提供原生文件时索引标记 unverified，后续必须回原 CLI 核对。检索命中时只读相关摘要，不把 rsi/sessions 全目录作为常驻上下文。

最小用法：从治理根目录的 templates/rsi-task-state.json 复制一份输入文件（业务项目通常是 docs/governance/templates/rsi-task-state.json），填入经核对的状态；执行 python scripts/rsi_checkpoint.py save --project-root <项目根> --task <任务ID> --input <输入JSON>。续跑先执行 python scripts/rsi_checkpoint.py resume --project-root <项目根> --task <任务ID>。exit 1 表示漂移，exit 2 表示状态缺失或不合法。评测数据为 JSON 数组，每条含 task_id、passed、rework_steps、recovery_minutes、input_tokens、critical_misses；比较命令为 python scripts/rsi_evaluate.py --baseline <旧数据> --candidate <新数据>。同一对任务必须保持模型、工具、验收标准和环境一致，并保存原始运行日志及人工验收依据；否则指标不用于晋升。

## 2. 压缩与续跑协议

- 在明确的可验证阶段边界、会话交接或跨机器交接时按需保存任务状态；不能拦截 CLI 自动压缩，也不能要求每次原生压缩先运行外部脚本。高风险操作和超过十分钟的 loop 可在阶段完成后保存。
- 恢复时先读快照、核对 Git HEAD/工作树指纹及工件 SHA-256；不一致则先查当前文件及提交，不能直接复用旧的下一步。无 Git 时必须至少列出可验证的工件引用。
- 模型只加载当前任务所需的规则、事实和证据；无法从聊天摘要复原的状态必须标未知，重新验证。
- 未提交/未同步的本机改动不会因共享治理仓自动出现在其他机器；交接前仍须提交并推送，或以明确的受控工件传输。共享检查点也不能恢复丢失的代码字节。
- 任务快照不得包含口令、访问令牌或大段会话原文。默认本地 _logs/ 被 Git 忽略；跨机共享需要单独设置访问控制、保留期和冲突策略。
- 共享状态目录目前只支持**单任务单写者**：同一 task_id 不得由两台机器并发 save。接管前先核对原机器停写及任务归属；存在并发风险时，分别用不同 task_id，人工审阅后合并到新的检查点。脚本不提供分布式锁、冲突自动合并或数据库事务保证。

## 3. 改进循环与晋升门

Observe → Hypothesize → Isolate → Evaluate → Review → Promote/Rollback。

1. 观察失败样本，记录基线模型、任务、环境、版本和原始证据。
2. 一次只改变一个可归因的治理或工具变量；用 Revision 候选记录预期改进和回退方式。
3. 在同一批任务上比较 baseline/candidate，至少覆盖上下文压缩后续跑、跨机交接、错误恢复和正常任务；任务集不得只由候选方案挑选。
4. 执行 scripts/rsi_evaluate.py。默认门：至少五个配对任务，无单任务通过→失败回归；总通过数不降；关键遗漏、返工步骤、恢复分钟数不增；输入 token 增幅不超 20%。这只是**候选可评审门**，不是统计显著性证明。
5. 未通过则回退或迭代候选；通过后仍需审查测试覆盖、跨模型可迁移性与安全边界，最后才合并权威仓。

## 4. 明确边界

- 此机制降低可持久化信息的遗失风险，但无法恢复从未记录的推理、隐含意图或未同步工件。
- Snapshot 的工作树指纹只用于发现漂移；不是内容备份。恢复必须以 Git、文件和测试结果为准。
- Rule 和 loader 的路由命中率也需要单独评测；上下文越短不意味着正确率越高。
- 对创作与研究任务，除代码测试外还须保存源素材、版权/许可、取舍依据及人工验收标准。
