# 建模与状态机思维

## 1. 目标

将复杂流程显式建模为状态机或事件驱动系统，使状态转换可追踪、可验证、可恢复。

## 2. 核心原则

- 规则匹配、请求处理、配置装载、模块初始化和发布流程都应被视为显式状态流，而不是隐式副作用集合。
- 设计或修改时应说明输入、状态转换、失败路径和恢复路径。
- 跨模块共享状态应避免靠隐式全局变量和时序假设维持。

## 3. 应用场景

- 订单/支付/审批等业务流程建模
- 连接/会话/事务的生命周期管理
- 构建/部署/发布流水线的阶段控制
- 用户交互流程（向导、表单、多步操作）

## 4. 设计要求

- 每个有生命周期的实体必须有显式的状态枚举。
- 状态转换必须声明合法的迁移路径，禁止任意跳转。
- 每次状态迁移必须记录：触发事件、前置条件、副作用。
- 终态和异常态必须有明确定义（成功完成/超时/取消/失败）。
- 状态持久化策略必须显式选择（内存/数据库/事件溯源）。

## 5. 评审问题

- 这个流程能画出完整的状态图吗？
- 所有状态迁移的触发条件和前置条件是否明确？
- 是否存在状态死锁或无法到达的终态？
- 异常中断后，恢复机制是什么？
- 并发场景下，状态竞争如何处理？

## 6. 验证重点

- 状态枚举是否覆盖所有可能的系统状态
- 状态迁移图是否无死锁和不可达状态
- 异常态是否有恢复或补偿路径
- 并发状态修改是否有冲突解决机制
